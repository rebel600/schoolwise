# ADR-0006 — Drizzle ORM instead of Prisma

**Status:** Accepted
**Date:** 2026-08-02

---

## Context

The original documentation recommended Prisma, with TypeORM as an alternative.

The decision to make multi-tenancy a v1 requirement ([ADR-0004](0004-multi-tenancy-in-v1.md)) changed the evaluation criteria. Tenant isolation depends on three capabilities:

1. Composing a mandatory `school_id` predicate into every query, generically
2. Setting a per-request PostgreSQL session variable so Row-Level Security policies apply
3. Writing analytical SQL for reporting without leaving the type system

Prisma's client is deliberately opaque. Injecting a predicate into every query means either wrapping every model method by hand or relying on client extensions, and driving RLS session variables requires dropping to `$executeRaw` on a connection whose identity the pool does not guarantee.

## Decision

**Drizzle ORM with PostgreSQL.**

- Schema defined in TypeScript under `packages/backend/src/database/schema/`
- Migrations generated by `drizzle-kit` and committed to source control
- A `TenantRepository` base class composes `eq(table.schoolId, ctx.schoolId)` into every query
- Per-request `SET LOCAL app.current_school_id` inside a transaction activates RLS policies
- Zod schemas derived from Drizzle tables via `drizzle-zod`, shared with the frontend through `@school-wise/lib-types`

## Alternatives Considered

**Prisma, as documented.** Excellent DX, mature migrations, strong type safety. Rejected: the query engine is a separate binary adding cold-start latency, the client is hard to extend generically for tenant scoping, and RLS integration is awkward. Prisma is the better choice for a single-tenant application — it is not the better choice here.

**TypeORM.** Rejected: weaker type inference, and its active-record and data-mapper patterns invite business logic into entities, which conflicts with the layering in `docs/03-backend.md`.

**Raw SQL with a query builder (Kysely).** Excellent types and full SQL control. Rejected: no migration tooling, and no schema as a single source of truth.

## Consequences

- SQL fluency is required. Drizzle's API mirrors SQL rather than abstracting it — an advantage for reporting queries, a steeper start for developers who have only used an ORM.
- Relational queries are more explicit. Drizzle has no equivalent to Prisma's nested `include` graph; joins are written out.
- No separate query engine binary. Faster cold starts and a smaller container image.
- Tenant scoping and RLS integration become straightforward, which was the deciding factor.
- Migrations are plain SQL files — reviewable in a pull request, which the "migrations must be reviewed before deployment" rule in `docs/03-backend.md` requires.
- Consistent with the Drizzle usage in the adjacent Taxorix codebase, so the team carries existing knowledge over.
